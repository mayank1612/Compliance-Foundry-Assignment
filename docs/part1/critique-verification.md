# Verification of the AI Critique

**What this is:** a point-by-point check of [`ai-critique.md`](ai-critique.md) against the schema v1 code, Postgres semantics and measurements. It is evidence for the authors' assessment in [`critique-analysis.md`](critique-analysis.md), not that assessment itself.

**Method:**

- **Reading:** every finding's file and line references were checked against the code at `schema-v1`. All the spot-checked references were accurate.
- **Probes:** 14 probes ran on a 20,000-task seed (4,000 cards per status), mostly as `app_user` with row-level security on, using `EXPLAIN (ANALYZE, BUFFERS)` and direct reads and writes.
- **Reasoning:** PGlite is a single database session, so the three race-condition findings (C2, C3, C4) can't be reproduced on it. They were checked against Postgres's documented locking and visibility rules instead.

## Answers to the critique's open questions

| Question                              | Answer from the design                                                                                                                                                                                                           |
| ------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Isolation level?                      | READ COMMITTED (Kysely's default; `withUserContext` sets none), so C2 and C4 apply as reasoned                                                                                                                                   |
| Which role does the pool log in as?   | The owner role (a superuser on PGlite). Requests drop to `app_user` inside `withUserContext`. **Any query outside it bypasses row-level security entirely**, so Part 2 must make that wrapper the only way to reach the database |
| Do raw database errors reach clients? | Not by design: GraphQL Yoga masks unexpected errors. That reduces SEC3 to its lock-contention part                                                                                                                               |
| Is account deletion a feature?        | Not yet. I1 becomes urgent the day it is. Today a sole owner can't delete their account (intended)                                                                                                                               |
| Can viewers be assignees?             | Currently yes (the foreign key allows any member). That's a product decision the schema didn't make explicitly                                                                                                                   |
| Retention for `task_activities`?      | None yet. 1.2 names it the first candidate for partitioning                                                                                                                                                                      |
| Are `text_gt` / `text_lt` leakproof?  | **Yes**, verified on Postgres 18. That's why half of S2 doesn't hold                                                                                                                                                             |
